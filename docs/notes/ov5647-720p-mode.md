# OV5647 native 1280x720@60 mode — reference

Living reference for the native 720p camera mode used by `apriltag_demo` and
`tinytag_detect`. Supersedes the status parts of
[`native-720p-2026-09-02.md`](native-720p-2026-09-02.md), which records the
initial bring-up only and predates the lens-shading fix.

Relevant commits: `b27c25e` (mode added), `f717dcb` (lens-shading fix).


## 1. What it is and why

`b27c25e` added a second OV5647 sensor mode — a 2x2-binned 1280x720 readout at
60 fps — alongside the existing 1920x1080@30. Both tag apps ask for it in
preference to 1080p.

The point is **latency**, not resolution. Previously the sensor ran at 1080p30
and the ISP downscaled to 1280x720; the detector saw the same 1280x720 image
either way. The native mode halves the readout interval (16.7 ms vs 33.3 ms),
so a frame handed to the detector is fresher, and it removes the ISP downscale
stage. It is *not* a throughput win — see §7.


## 2. How the mode is chosen

Both apps make the identical call at startup — `apriltag_demo/src/main.cc:845`
and `tinytag_detect/main.cc:652`:

```c
v4l2_drm_request_sensor_mode(kd_mpi_get_vvcam_video00(),
                             1280, 720, 60,     /* preferred */
                             1920, 1080, 30,    /* fallback  */
                             &sensor_width, &sensor_height, &sensor_fps);
```

**The literals are hardcoded. There is no command-line flag or environment
variable to pick the mode.** In particular `apriltag_demo --csi-size WxH` is
*not* that switch: it only sets the V4L2 capture format requested on the video
node (`main.cc:789` → `main.cc:207`) and never reaches the sensor-mode call.
Asking for more than the sensor mode supplies silently negotiates back down:

```
$ ./apriltag_demo.elf --csi-size 1920x1080
[input] sensor selected 1280x720@60 (preferred)
[input] CSI requested 1920x1080, negotiated 1280x720 stride=1280
```

Selection (`v4l2-drm/src/lib.c:175`) has two steps, and **both** must succeed
or it falls through to 1080p:

1. `vvcam_sensor_find_mode(active_sensor, W, H, fps)` — does the active
   sensor's driver advertise the mode?
2. `v4l2_drm_select_scene_profile(cfg, W, H)` — is there ISP tuning for it?
   This first greps the *active* scene XML for the literal string `"WxH"`; only
   if that misses does it derive `<stem>-WxH.{xml,manual.json,auto.json}`,
   require all three to exist, and require the derived XML to contain `"WxH"`.

Check which branch you got — the app prints it:

```
[input] sensor selected 1280x720@60 (preferred)      <- native 720p
[input] sensor selected 1920x1080@30 (fallback)      <- 1080p, ISP downscales
```


## 3. Effect on other cameras / boards: none

Only OV5647 has a 720p mode. Verified across the sensor drivers in
`package/vvcam/src/`:

| driver | modes advertised |
|---|---|
| gc2093, gc2053, bf3238 | 1920x1080 |
| imx335 | 1920x1080, 2592x1944 |
| **ov5647** | 1920x1080, **1280x720** |

On a GC2093 board, step 1 above fails, the 1080p30 fallback is taken, and step
2 short-circuits on the first check because `gc2093-1920x1080.xml` already
contains the string `1920x1080`. No per-mode scene file is needed and the
board's own validated scene is untouched — behaviour identical to before
`b27c25e`.

The 720p profile generator in `package/vvcam/CMakeLists.txt` is likewise
guarded per-file (`if(profile STREQUAL "ov5647.manual.json")` / `"ov5647.xml"`)
and only iterates the three `ov5647.*` profiles. **This guard matters:**
`gc2093-1920x1080_manual.json` and `gc2053-1920x1080_manual.json` contain the
*same* 32 x 60 `x_size` array, so an unguarded `string(REPLACE)` would silently
corrupt their lens-shading geometry. Keep the guard if you extend the
generator.


## 4. The lens-shading bug (fixed in `f717dcb`) — read this before touching tuning

### Symptom
Heavy horizontal streaking in the **luma** plane, rectangular blocks of
differing brightness, vertical band boundaries, and a blue-centre/green-edge
colour split. AprilTag decode failed on every frame (`ok=0`). AE railed at its
24x maximum.

### Root cause
The 720p ISP profile is *generated* from the validated 1080p profile by string
substitution. The lens-shading mesh is stored as 33x33 gain samples **plus
sector tables `x_size`/`y_size` that state, in pixels, how far apart those
samples sit** — i.e. a statement about the frame the mesh was calibrated
against:

```
x_size: 32 entries of 60   = 1920 columns
y_size: 16 entries ~33.75  =  540 (half of 1080)
```

The substitution relabelled the profile `1280x720` but left both tables
describing a 1920x1080 frame, so the ISP walked the mesh with a row pitch that
overran the shorter frame. The gain field it applied was smooth along each row
and jumped chaotically between rows — a per-row gain error, which is exactly
horizontal banding.

### Fix
Rescale both tables by 2/3 in the generator: `x_size` 32x60=1920 → 32x40=1280,
`y_size` sum 540 → 360. The mesh **samples** are deliberately untouched.

### The trap to remember
The runtime mesh comes from the **`CLscv2` block in `*.manual.json`**, not from
the XML. The XML's `LSC_SECT_SIZE_X/Y` is rescaled too for consistency, but
editing the XML alone changes nothing — that was a wasted iteration during the
original debug.


## 5. Where things live

| what | path |
|---|---|
| Sensor register tables + mode metadata | `package/vvcam/src/ov5647.c` |
| 720p profile generator (the LSC rescale) | `package/vvcam/CMakeLists.txt` |
| Source 1080p tuning (never edited for 720p) | `package/vvcam/configs/ov5647.{xml,manual.json,auto.json}` |
| Generated 720p tuning (build output) | `/etc/vvcam/ov5647-1280x720.{xml,manual.json,auto.json}` |
| Mode selection + scene resolution | `package/vvcam/v4l2-drm/src/lib.c` |
| Capability lookup (mode table query) | `libvvcam-capabilities.so` |

Rebuilding after a generator change needs the overlay sync — a plain
`make vvcam-rebuild` from inside `output/<defconfig>/` will silently use a
stale copy:

```sh
make CONF=k230_canmv_v3_defconfig sync
make CONF=k230_canmv_v3_defconfig vvcam-dirclean
make CONF=k230_canmv_v3_defconfig vvcam
```


## 6. Diagnosing camera image faults on this stack

### The metric
On a dumped Y plane, compare mean |diff| of adjacent **row** means ("rowdiff")
against adjacent **column** means ("coldiff"). Clean frame: rowdiff ~ coldiff.
Horizontal banding: rowdiff >> coldiff. Gives one number to A/B against
instead of eyeballing.

`apriltag_demo --debug` with `APRILTAG_DEMO_DUMP=<path>` writes the Y plane
when you press `q` (needs `ssh -tt`); one dump per run.

### Split sensor vs ISP — do this first
`/dev/video4` is the ISP raw-passthrough pad and **streams concurrently while
an app holds `/dev/video1`** (`/dev/video2`/SP1 does not — it returns 0 bytes):

```sh
v4l2-ctl -d /dev/video4 --set-fmt-video=width=1280,height=720,pixelformat=GB10 \
  --stream-mmap --stream-skip=3 --stream-count=1 --stream-to=/tmp/raw.bin
```
16-bit LE, 10 valid bits LSB-aligned; file = W*H*2. Compare rowdiff/coldiff on
one Bayer plane (`r[0::2,0::2]`). Clean RAW ⇒ the fault is in the ISP. This is
what exonerated the sensor and its register table in the banding hunt.

### Bisect the ISP
Modules expose named V4L2 controls on the streaming node:

```sh
v4l2-ctl -d /dev/video1 --set-ctrl=isp_lsc_enable=0
```
Available: `lsc, dpcc, ee, ge, dmsc (+sharpen/demoire/dpl/cac/skin), gc, ccm,
cproc, awb, ae, af`. `v4l2-ctl -d /dev/video1 -L` lists them (values only read
back while streaming). **Keep `gc` (gamma) enabled while bisecting** — turning
it off darkens the frame and masks noise, which looks like a fix.

### The gotcha that produced a false result
**The selected sensor mode is held kernel-side in the vvcam ISP driver.**
Restarting `isp_media_server`, or loading an older `libv4l2-drm.so`, does *not*
return the sensor to 1080p. During the original debug this produced a "1080p
control" that appeared to show the same artifact and nearly exonerated the 720p
mode entirely.

Any mode-related A/B must **reboot the board** and **verify the live mode over
I2C**:

```sh
i2ctransfer -y 0 w2@0x36 0x38 0x14 r1   # 0x3814: 0x11 = 1080p, 0x31 = 720p binned
i2ctransfer -y 0 w2@0x36 0x30 0x36 r1   # 0x3036 PLL: 0x62 = 1080p, 0x6e = 720p
i2ctransfer -y 0 w2@0x36 0x35 0x00 r3   # exposure, value>>4 = lines
i2ctransfer -y 0 w2@0x36 0x35 0x0a r2   # analog gain, value/16 = x
```
Use `i2ctransfer`, not `i2cget` — the latter can't do 16-bit register addresses.

Also note: on a fresh boot the sensor does not answer on I2C until something
configures it, so a successful read already implies an app or
`isp_media_server` has run.

### Board quirks that cost time
- No `pkill`, no `timeout` on the board.
- `/etc/init.d/S31canaan_isp` has **no restart handling** — re-running it
  spawns a *second* `isp_media_server`. Kill by PID, relaunch with `setsid`.
- python3 + numpy exist but OOM on ~110 MB arrays while an app runs; sample
  frame-by-frame instead of capturing a large burst.


## 7. Measured performance trade-off

Same detector, same 1280x720 detector input in both cases, same scene:

| sensor mode | camera | display | **detect** |
|---|---|---|---|
| native 720p@60 | ~53 fps | ~60 fps | **~9 fps** |
| 1080p@30 (ISP downscale) | ~28 fps | ~42 fps | **~15 fps** |

Detection is *slower* in 720p. This is **CPU contention, not extra detection
work** — quad counts per frame are comparable (q ~ 13-26 vs 22-26). Linux runs
on a **single core** here, and `/proc/stat` showed **exactly zero idle ticks**
over a 5-second sample during a 720p run, so the doubled capture and display
work comes straight out of the detection thread's budget.

So the mode buys latency and costs detection throughput. Note the table is
**apriltag_demo**, which still holds the camera buffer for the whole pipeline
*and* across its OSD write. `tinytag_detect` already releases the buffer right
after the ROI crops are copied (`b27c25e`), so it is far less exposed to this.
The capture-requeue split is what lets 720p deliver latency *and* throughput —
see `perf_todo.md` §2/§3A/§5.


## 8. Known issues

**Residual colour shading (expected).** Only the mesh *geometry* was corrected;
the samples remain 1080p-derived. The 720p mode reads a substantially wider
region of the pixel array than 1080p (2576x1452 vs 1928x1088), so its true
vignetting profile differs and the periphery is under-corrected. It presents as
a centre-vs-edge colour cast that shifts with lighting, because the profile
carries five per-illuminant meshes (A/D50/D65/F11/F12) that AWB selects among.
Proper removal needs a 720p flat-field calibration. The luma-only path (§9)
hides it on the preview.

**Slow overall brightness flicker (unresolved).** Reported visually in 720p and
not explained. Ruled out by measurement:

- *Sensor AE hunting* — exposure and analog gain sampled over ~15 s were
  bit-identical throughout (0x3501/0x3502 = 0x1fd0 → 509 lines).
- *Mains-flicker beat* — forcing exposure to exactly one 60 Hz ripple period
  (425 lines = 8.33 ms) with AE frozen changed nothing.
- *The sensor/optical path generally* — RAW10 frames from the raw-passthrough
  pad are flat both at frame rate (60 consecutive frames: 0.31% peak-to-peak,
  0.09% std) and over a 50 s baseline (25 samples: 1.37% p-p, 0.42% std, and
  that is a slow monotonic drift, not an oscillation).

Since RAW is flat, whatever modulates brightness is **downstream of the raw
tap** — ISP or display path. That is where to resume. An A/B against the
pre-luma-only binary appeared once to remove it but did **not** reproduce on a
clean rebuild, so luma-only is not the cause.


## 9. Dead ends — do not retry

- **Sensor register table.** `0x3036 0x6e→0x62` and `0x5002 0x00→0x41` (chosen
  to match the repo's 1080p table and mainline's binned modes) were built,
  deployed and tested; neither changed the artifact. `0x3036=0x62` is actively
  harmful — it lowers the PLL below 60 fps (~53) and breaks the `0x3036`/
  `0x4837` MIPI-timing pairing (`0x4837=0x16` is matched to `0x6e`). The
  sequence as ported from Canaan's mode-6 table is correct.
- **`0x3820` bit 6.** Mainline's binned OV5647 modes use `0x3820=0x41` where
  this table uses `0x01`. Poking `0x41` into the live streaming sensor moved
  rowdiff only 7.33 → 7.00.
- **Luma-only as a banding fix.** Desaturating via ISP CPROC cannot work: the
  corruption was in Y, not chroma. `v4l2_drm_set_luma_only()` is nevertheless
  kept, on different grounds — both apps read only Y, it is one setup call with
  zero per-frame cost, and it hides the §8 chroma artifacts on the preview. It
  is a preview-path choice, not a fix.
- **Rescaling the XML LSC tables alone.** No effect; the runtime mesh comes
  from `manual.json` (§4).
