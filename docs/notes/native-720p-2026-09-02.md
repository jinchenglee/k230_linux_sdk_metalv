# Native OV5647 1280x720 capture — 2026-09-02

> **Status: historical.** This note records the initial bring-up (`b27c25e`)
> and predates the lens-shading fix (`f717dcb`). Two things below are now
> known to be wrong: the poor image quality was a *bug* in the generated 720p
> ISP profile, not merely uncalibrated tuning (see §4 of the reference), and
> the "Y-only/raw path contingency" mentioned under *Limitations* cannot work
> as a fix, because the artifact was in Y rather than chroma.
> For current behaviour, selection rules, diagnostics and known issues see
> [`ov5647-720p-mode.md`](ov5647-720p-mode.md).

## Goal

Give `apriltag_demo` and `tinytag_detect` a generic preferred camera request of
1280x720 at 60 fps, while retaining a 1920x1080 at 30 fps fallback. The apps do
not identify or hard-code a sensor model; the capture library asks the active
sensor capability table whether each mode exists. Other applications retain
the existing oldest-buffer capture behavior and default camera mode.

## Implementation

- Added the OV5647 1280x720@60 sensor register sequence and mode metadata to
  `package/vvcam/src/ov5647.c`. Mode 0 remains 1920x1080@30 and mode 1 is the
  new native 1280x720@60 mode.
- Added `libvvcam-capabilities.so`, a standalone capability lookup library that
  does not depend on the closed `isp_media_server` registration callback.
- Added `v4l2_drm_request_sensor_mode()` to `libv4l2-drm`. It reads the active
  private scene controls, resolves a mode by width/height/fps, selects a
  per-mode scene when available, and falls back to the existing scene/mode.
- Both applications call this additive API before capture setup.
- Per-mode scene names follow the generic convention
  `<active-stem>-<width>x<height>{,.manual,.auto}.<ext>`. This allows a future
  camera to supply its own calibrated profiles without adding sensor-specific
  app logic.

## 720p scene starter

No externally downloadable K230-compatible OV5647 720p ISP bundle was found.
The installed starter files are mechanically derived from the validated
OV5647 1080p files:

- `ov5647-1280x720.xml`
- `ov5647-1280x720.manual.json`
- `ov5647-1280x720.auto.json`

The XML profile labels and scalar header dimensions are changed to 1280x720;
the tuning tables themselves are not recalibrated. Consequently, image
quality is expected to be inferior until the 720p scene is tuned. The K230
documentation confirms that XML, auto JSON, and manual JSON are runtime VICAP
calibration inputs and must match the VICAP/ISP version:
<https://www.kendryte.com/k230/en/v1.9/01_software/board/mpp/K230_VICAP_SENSOR_Parameter_Partition_Reference.html>.

## Board deployment and verification

Target: `root@192.168.10.125`, `k230_canmv_v3_defconfig`, after reboot.

Deployed to `/usr/lib` and `/etc/vvcam`:

- rebuilt `libv4l2-drm.so`;
- the three 720p starter scene files.

The previous capture library was preserved as
`/usr/lib/libv4l2-drm.so.safe-prev` during the test.

### TinyTag

The existing launcher ran successfully and reported:

```
v4l2-drm: using per-mode scene ov5647-1280x720.xml (starter tuning)
[input] sensor selected 1280x720@60 (preferred)
[input] CSI requested 1280x720, negotiated 1280x720 stride=1280
```

The LCD displayed a live image. Kernel logs showed the expected 1280x720 NV12
allocation and no VICAP/MIPI error, vb2 warning, timeout, or Oops.

### AprilTag

The existing AprilTag binary also selected and streamed the same mode:

```
[input] sensor selected 1280x720@60 (preferred)
[input] CSI requested 1280x720, negotiated 1280x720 stride=1280
```

During the short run, camera throughput was approximately 50–53 fps, display
was approximately 60 fps, and scalar detection was approximately 14 fps with
the default factor-2 configuration. No kernel errors were observed.

## Limitations and next work

The 720p mode is functionally working, but the starter ISP profile is not
calibrated. Expected follow-up work is capture-based ISP tuning of exposure,
white balance, noise reduction, color, and lens shading. The Y-only/raw path
remains a contingency for AprilTag, but is intentionally not used because it
would permanently lose the color/UV path.

The board should be returned to the validated 1080p scene before testing other
applications if they do not use the new mode-selection API. The fallback path
is retained for sensors or modes without a matching capability/profile.
